# BrightFX

A portable particle-effects engine and authoring tool. One simulation core,
compiled for the web, macOS, and Windows — so an effect behaves identically
everywhere it runs.

> **Status: early.** The simulation core, its FFI boundary, and its renderer
> are built and verified. There is no authoring UI yet — see
> [Where this is](#where-this-is).

## Why

BrightFX generalizes the particle system from
[Mouseflare](https://github.com/OffBy1-tech/Mouse-Flare), which made the mouse
cursor visible with configurable trails and bursts. That project carried three
independent renderers — web, macOS, Windows — implementing the same particle
rules, kept in sync by hand. They drifted.

BrightFX exists to have exactly one implementation of those rules, and to make
the effects general: any moving point can drive them — a game object, a
keyframed camera target, a cursor — not just a mouse.

## Architecture

```
brightfx-core          the simulation and the rasterizer. pure Rust, no platform code
    ├── render         shapes, glow, blend modes → a premultiplied RGBA8 frame
    └── abi            the FFI boundary's logic, also pure Rust
         ├── brightfx-ffi    C ABI  (cbindgen)  → macOS (Swift), Windows (C#)
         └── brightfx-wasm   wasm-bindgen        → web (JS)
brightfx-tracks        track generators: timing data in, baked emitter tracks out. pure Rust
packages/brightfx-js       typed wrapper over the web wasm build (npm)
packages/brightfx-remotion Remotion component: frame mode (canvas) and sprite mode (render prop)
presets/               the preset library, generated by brightfx-tracks/examples/gen_presets
```

The two wrapper crates contain **no logic**. Every exported function is a type
translation around exactly one `abi` call. That constraint is the whole design:
behavior lives in one place, so the bindings cannot disagree.

The hot path is zero-copy in both directions. Rust writes particle state into
a preallocated buffer and hosts read it in place — a `Float32Array` view
over WASM linear memory, an `UnsafePointer<Float>` in Swift, a pointer in
C#. The frame is the same: the core rasterizes into its own buffer and the
host blits it. No marshaling per particle or per pixel; the frame and
particle buffers are preallocated, though rasterizing a stroked shape still
allocates its polygons per frame.

## Using it

```
sim = new(seed)                      // starts from a default config
set_config(json) -> envelope         // {"ok":true,"clamped":[...],"warnings":[...]} | {"ok":false,"error":"..."}

// per frame
set_emitter(x, y, vx, vy, active)
advance(dt)
read particle_count() * particle_floats() floats at buffer_ptr()

// scrubbing, when the config carries an emitterTrack
seek(time)

// drawing
set_viewport(width, height, scale) -> envelope    // device pixels, and pixels per logical unit
render()
read frame_len() bytes at frame_ptr()             // premultiplied RGBA8, stride width * 4
```

Each particle is 8 `f32`: `x, y, size, rotation, r, g, b, a`.

`core/README.md` documents the boundary's contract — atomic config rejection,
live parameter edits, panic poisoning, and the WASM memory-detachment trap.
`core/brightfx-core/README.md` covers the simulation crate itself, including
which config fields it deliberately ignores.

## Effects

A `.brightfx.json` effect is a single config object: emitter behavior (rate,
burst size, emission pattern, spread, velocity inheritance), physics (gravity,
drag, turbulence, vortex), lifetime and size curves, and color. The vocabulary
carried today: **14 shapes**, **6 emission patterns**, **6 color modes**,
**4 size curves**, **4 blend modes**.

Configs are read permissively — out-of-range values are clamped rather than
rejected, and the result envelope reports which fields were adjusted so a UI
can say so.

An optional `emitterTrack` holds keyframed position and timed triggers, which
lets the core drive itself end to end. That is what makes an exported effect
self-contained for offline rendering, rather than needing a host to feed it a
position every frame.

## Where this is

**Built and verified**

- The simulation core: schema, deterministic seeded RNG, fixed-capacity
  particle pool, physics, lifetime/size/color curves, baked-timeline playback.
- The FFI boundary: C ABI and WASM, from one shared pure-Rust module.
- Cross-language verification — Node, Swift, and C# each replay identical
  protocols from shared fixtures and must reproduce the same particle
  buffers, both driven live and seeked from a baked emitter track.
- Rendering: the 14 shapes, glow, and the four blend modes rasterized in
  core into a premultiplied RGBA8 frame, guarded by a golden frame that
  Node, Swift, and C# each reproduce.
- Continuous integration: every push to `main` and every pull request runs
  the full verification suite on a macOS runner, and the Rust tests plus
  the C# harness against a real `brightfx_ffi.dll` on a Windows runner.
- Render budget: 500 glowing particles at 1280×800 render in about 3.6 ms
  on Apple M3 for the reference scene, under the 4 ms target; see
  `core/brightfx-core/README.md` for every shape.
- Forward seeking: `seek` runs through the grid point at or after the
  requested time, stepping from the last seek instead of replaying; a
  fixture has all three harnesses prove forward == fresh bit for bit.
- Track generators: `fit_track`, `sweep_track`, and the lyric-cue
  generator in `brightfx-tracks`, exposed through wasm; the Node harness
  replays a recorded fixture through the wasm build.
- Packages: `brightfx-js` and `brightfx-remotion` under `packages/`, with
  a still-image test proving the component adds nothing to the core's
  frame.
- Presets: seven effects under `presets/`, generated from code, each with
  a golden frame.

**Not built yet**

- **Authoring tools.**
- Sharing, a preset gallery, and game-engine export.

Known gaps and deferred work are tracked in
[issues](https://github.com/OffBy1-tech/BrightFX/issues).

## Verifying

```bash
rustup target add wasm32-unknown-unknown
cargo install wasm-pack
cargo install cbindgen --version 0.29.4   # pinned: version churn trips the header guard

./core/scripts/smoke-all.sh
```

That runs the Rust tests, checks the generated C header is current, confirms a
verify run did not rewrite the fixtures, then replays the protocol through all
three language harnesses.

Two of those steps are guards against failures whose symptom is a *passing*
test: a stale C header shipped to the native apps, and a fixture silently
re-baselined instead of verified. Both were added after they nearly slipped
through.

CI (`.github/workflows/smoke.yml`) runs the same script on every push to
`main` and every pull request, so a green check means all of the above
passed on a clean macOS runner. A second job builds the C ABI for MSVC on
Windows and runs the Rust tests and the C# harness there, so the P/Invoke
contract is checked against the library the Windows app will actually load.
